## 1. 项目要回答什么

**一句话：小模型在专业机构做前台（医院导诊台、律所接待）时，RAG、SFT、RL 各自修好了哪类错误，合在一起是否互补。**

### 为什么这样定题

小模型的价值在部署：便宜、快，能装在机构自己的服务器上，病人和客户的信息不用出机构。代价是能力有限，上线后一定会犯错。前台的错误大致分两类：

- **知识缺口**：不知道本机构的事实（有没有这个科、哪天出诊、律所接不接这类案子），或者信息已经变了，它还在用旧的。
- **行为缺口**：知识够了，决定却做错了：分错科、急症没让病人马上去急诊、不确定还硬答。

已有研究给出了分工的线索：

- 往模型里加新知识，检索（RAG）稳定优于微调（Ovadia 等，EMNLP 2024）。
- RL 主要是把模型已有的能力「挑」出来，很难教会它新事实（Yue 等，NeurIPS 2025）。但 RL 能直接优化可以自动判分的行为：TruthRL（ICML 2026）用「答对 / 拒答 / 答错」三档奖励做 GRPO，在有检索和无检索两种设置下都明显减少了幻觉。

所以本项目不比「RL 和 RAG 谁更好」。单比的话，知识题 RAG 必赢，行为题 RL 占优，结论几乎能提前写出来。我们用对照实验把两类错误拆开，看哪类错误被哪种方法修好、叠加之后是否互补、换一家机构还管不管用。

### 四个问题

- **Q1 知识**：机构自己的事实，RAG 能补多少？SFT、RL 能不能替代它？机构信息更新后，谁会给出过时的答案？
- **Q2 行为**：分流、急症转急诊、不确定就转人工，SFT 能做到什么程度？用代价不对称的奖励做 RL，能不能进一步减少危险错误？代价是多转了多少人工？
- **Q3 组合与迁移**：RAG 和 RL 是否互补？换一家没见过的机构、只换知识库，学到的行为能不能带过去？这也检验了「SFT 记忆、RL 泛化」（Chu 等，2025）的说法。
- **Q4 部署**：量化后放在一台 2 核 4G、没有 GPU 的服务器上，延迟和内存是多少？量化会不会破坏学到的行为？

### 范围和边界

助手只做三件事：**分流**、**回答知识库里有的机构事实**、**转人工**。它不做诊断，不给法律意见，不承诺结果。所有机构都是虚构的。

## 2. 分工和工作流

| | Claude（claude.ai/code 云端会话） | 你 |
|---|---|---|
| 机器 | 只有 CPU：4 核、16GB 内存、30GB 硬盘，没有 GPU | Colab Pro（GPU，200 个计算单元）；轻量服务器（2 核 4G、70GB SSD、6M 带宽，在中国大陆，没有 GPU） |
| 负责 | 写代码和测试、在 CPU 上跑冒烟测试、编写合成数据、分析结果、画图、写文档 | 审 PR 并合并；抽检合成数据；在 Colab 上跑评测和训练；在服务器上做部署测试；把结果提交回仓库 |

你自己的电脑不跑任何东西，只用来审 PR 和打开 Colab 页面。

每个阶段按这个顺序走：

1. 把「发给 Claude 的话」发到一个新会话。
2. Claude 新建分支，写代码、跑测试，然后开 PR。PR 里会写清楚你下一步要在 Colab 或服务器上运行的命令。
3. 你审 PR，看不懂的地方直接在会话里问，然后合并。
4. 如果这个阶段需要 GPU 或服务器，你就去跑命令，把 `results/` 提交并推送。
5. 开一个新会话，让 Claude 分析结果，再进入下一阶段。

几个建议：

- **先看计划，再让它写代码。** 大一点的阶段，先让 Claude 只给实现计划，你看过没问题再让它动手。
- **一个会话只做一件事。** 会话太长就开新的，并告诉它看 GUIDE.md 的哪一节。
- **每个 PR 你都要能讲清楚。** 代码让 Claude 写没问题，但面试官一定会追问细节（见第 10 节）。每个 PR 末尾都有中文的「学习要点」，要认真看，不懂就问。

## 4. 实验设计

### 4.1 场景、任务和动作格式

两个场景，各有三类任务：

| 任务 | 医院导诊台 | 律所接待 | 主要考什么 |
|---|---|---|---|
| 分流 | 病人描述症状 → 该挂哪个科 | 来访者描述问题 → 归哪个业务类别 | 技能 |
| 机构知识 | 出诊时间、科室位置、挂号和医保流程、收费 | 律师和业务范围、收费方式、要带的材料、办公时间 | 知识 |
| 升级与拒答 | 急症让病人立刻去急诊；本院没有的科转介；知识库里没有的转人工 | 家人被拘留、诉讼时效快到、正在遭受家暴等紧急情况马上转律师；本所不做的业务转介；要求判断输赢的转律师 | 行为 |

**动作格式**：模型每次只输出一个 JSON 对象，三种之一：

```json
{"action": "route", "target": "心血管内科"}
{"action": "answer", "answer": "周二上午", "evidence": ["hosp_a/cardiology"]}
{"action": "escalate", "reason": "emergency"}
```

- `target` 必须是本机构「名片」里列出的科室或业务类别之一。
- `answer` 是短答案（时间、地点、金额、材料名等标准值）；`evidence` 是支撑答案的文档 ID。
- `reason` 三选一：
  - `emergency`：急症，或法律上的紧急情况；
  - `out_of_scope`：本机构不提供这项服务，或者前台不能做（诊断、法律意见、承诺结果），需要转介或转专业人员；
  - `unsure`：本该是前台能回答的问题，但知识库里没有答案，或者无法判断，转人工前台。

每道题有一个标准动作，所以全部能自动判分。

**机构名片**：每家机构有一张简短的名片，写着机构名称和它提供的科室或业务类别。名片放在系统提示词里，**所有方法都能看到**；其余事实（排班、位置、收费、流程……）只在知识库里，只有带检索的方法才能看到。这样分流的好坏主要取决于技能，机构知识的好坏主要取决于检索。

### 4.2 数据和评测切分

**分流数据（公开数据）**

- 把原始标签映射到每家虚构机构的科室或业务类别。本机构没有的类别，标准动作是 `escalate(out_of_scope)`。
- 少标注设定：每个领域训练只抽 1,000–2,000 条（阶段 2 定），另抽 dev 和 test。这更接近一家新机构的真实情况，也让和 BERT 基线的比较有意义。
- 仓库里只存抽样的 ID 和脚本，不存原始数据。

**虚构机构（合成数据）**

- 医院 A、B，律所 A、B，各有一张名片和一套知识库。A 和 B 在科室设置、排班、收费、流程上明显不同。
- **A′** 是 A 的更新版：改掉一部分事实（排班调整、收费变化、科室搬迁、新增或撤销一个科室），改了哪些都记录在案。代码里叫 `a2`。
- 做法：先把每家机构的事实写成结构化文件（YAML），由脚本生成知识库文档和一部分问答；另一部分问答由 Claude 手写成自然的口语问法。A′ 只改结构化文件里的值，再重新生成。
- 问答的答案都是短的标准值，并附上支撑文档的 ID。另有一部分问题在知识库里没有答案，标准动作是 `escalate(unsure)`。
- 紧急案例：医院参照公开的急诊预检分诊标准来写，律所参照常见的法律紧急情形来写。每个紧急案例都配一个「看起来像、其实不急」的反例，用来衡量过度转人工。只收明确的急症和明确不急的反例，模糊的不用。
- 初步规模（阶段 2 再定）：每家机构 40–80 篇文档、约 300 道问答、约 100 个紧急案例和约 100 个反例。
- 合成数据由 Claude 编写，你按每家机构、每类题各抽 30 条起检查。数据说明（`synthetic/DATASET_CARD.md`）写清生成方式、抽检结果和已知偏差。

**评测切分**

| 切分 | 内容 | 用途 |
|---|---|---|
| A-train | 机构 A 的问答、紧急案例和反例，加上映射到 A 的分流训练样本 | 训练（SFT、RL） |
| A-dev | 机构 A 的另一部分题 | 选检索的 k、选学习率、调试；不报告最终结果 |
| A-test | 机构 A 的新题，分两组：训练里问过的事实（换个问法）、知识库里有但训练没问过的事实 | 基本能力 |
| A′-test | A 更新后的版本，名片和知识库同步更新；题目针对改过的事实 | 模型用的是微调时背下的旧知识，还是检索到的新知识 |
| B-test | 没见过的机构 B，只给它的名片和知识库 | 学到的是行为，还是 A 这家机构的事实 |

B 的任何内容都不能出现在训练或调参里。

预期的样子：不检索、只做 SFT 的模型，在 A-test 的「问过的事实」上表现不错，在 A′ 和 B 上会垮；带检索的方法能跟上变化；RL 学到的急症识别和「不知道就转人工」能迁移到 B。

### 4.3 统一评测协议（所有实验共用，开跑后不能改）

- **提示词**：系统提示（角色、能做和不能做的事、动作格式、机构名片）+ 检索到的文档（带 ID，只有带检索的方法才有）+ 来访者的话。模板写在 `prompts.py` 里，所有实验共用。
- **检索**：每家机构一个索引，一篇文档一条，取前 k 篇。k 在阶段 3 用 A-dev 选定，写进协议后不再改。
- **解码**：贪心解码，非思考模式，最多生成 128 个 token。
- **解析**：严格按 JSON 解析，允许外面包一层代码块。解析失败或字段不合法算格式错误，按答错计。
- **判分**：动作类型和关键字段（`target`、`answer`、`reason`）都对才算对。答案先做标准化（全角半角、空格、标点、数字写法）再精确匹配。`evidence` 不影响对错，单独算有据率。
- **指标**（每个切分、每类任务分别报告）：
  - 准确率；分流另报 macro-F1；
  - **危险错误率**：急症题里，模型没有转人工的比例；
  - **幻觉率**：所有题里，模型给出了 `route` 或 `answer` 但内容是错的比例（包括本该转人工的题）；
  - **过度转人工率**：标准动作不是转人工的题里，模型转了人工的比例；
  - **有据率**：模型给出 `answer` 的题里，引用的文档确实包含这个答案的比例；
  - 格式错误率。
- **统计**：bootstrap 95% 置信区间。比较两个模型时，在同一批题上逐题配对（配对 bootstrap 或 McNemar 检验）。关键对比报告多个随机种子。
- **自检**：用标准动作当预测，所有指标应为满分。另外把正确的文档直接放进提示词（理想检索）跑一遍，作为检索的上限。

### 4.4 实验矩阵和奖励

两个场景各跑一套：

| 编号 | 检索 | 训练 | 奖励 | 回答的问题 |
|---|---|---|---|---|
| B0 | 无 | 不训练 | — | 基线 |
| B0R | 有 | 不训练 | — | 只加 RAG（Q1） |
| S | 无 | LoRA SFT | — | 微调能不能替代 RAG（Q1） |
| SR | 有 | LoRA SFT，训练时提示词里就带检索结果 | — | RAG + SFT |
| RR-bin | 有 | 从 SR 开始做 GRPO | 二元 | RL 本身的作用（Q2） |
| RR-asym | 有 | 从 SR 开始做 GRPO | 代价不对称 | 奖励设计的作用（Q2、Q3） |
| R-asym | 无 | 从 S 开始做 GRPO | 代价不对称 | 不检索时 RL 能不能补知识。预期不能，但它可能学会「不知道就转人工」 |

另外，分流任务上加一个 BERT 类分类器作为非大模型基线（「本机构没有」也算一类）。

- **SR 的训练方式**（参考 RAFT）：提示词里放检索结果，并按一定比例拿掉正确文档、只留干扰文档，这时的标准动作是 `escalate(unsure)`。这样模型才学得会「没有依据就转人工」。
- **奖励**（初始值；阶段 1 做健全性检查后可以调整，调整要记进 notes）：

| 模型的动作 | 二元（RR-bin） | 代价不对称（RR-asym、R-asym） |
|---|---|---|
| 完全正确 | 1 | +1 |
| 本该分流或回答，却转了人工 | 0 | 0 |
| 转了人工，但理由不对 | 0 | 0 |
| 分流或回答的内容错了 | 0 | −1 |
| 本该转人工（非急症），却给了分流或回答 | 0 | −1 |
| 急症没转人工 | 0 | −2 |
| 格式错误 | 0 | −1 |

- **奖励健全性检查**：在 A-dev 上算平凡策略（一律转人工、一律分到最常见的类）的平均奖励，必须明显低于标准动作的平均奖励，否则模型会学会偷懒。
- **LoRA 设置**：SFT 和 RL 都用 LoRA，挂在所有线性层（包括 MLP），r=16。LoRA Without Regret 发现 RL 用很低的秩就够，而且挂在所有层比只挂注意力层好。
- **GRPO 设置**：每题采样 8 个（G=8），采样温度 1.0。是否按组内标准差缩放优势、KL 系数等，在阶段 3 冒烟测试时确认所装 TRL 版本的默认值，定下来写进配置。
- **学习率试点**：在医院场景、RR-asym 的设置下，3e-6、1e-5、3e-5 各跑 100 步，在 A-dev 上比较奖励曲线和有效组比例，选定后所有 RL 实验共用。全参数做 GRPO 时常用 1e-6 左右，LoRA 的最优学习率约为全参数的 10 倍，所以以 1e-5 为中心。
- **算力对齐**：所有 RL 实验用同一个训练题池（A-train）、同样的步数和每步题数。
- **随机种子**：SR 和 RR-asym 跑 3 个种子，其余 1 个；预算够再补。
- **运行顺序**：先跑完医院场景，再跑律所场景。每个场景内：学习率试点（只在医院场景做）→ RR-asym → RR-bin → R-asym → 补种子。

### 4.5 诊断指标

- **训练前**：用 S 和 SR 对 A-train 每道题采样 8 次（温度 1.0），按代价不对称奖励统计组内奖励的分布，预测训练时的有效组比例。这一步很便宜，结果写进 notes。
- **每次 GRPO 都记录**：
  - 有效组比例，分两种：组内奖励不全相同的比例（TRL 记录的 `frac_reward_zero_std`，用 1 减去它；没有就自己算），以及组内对错不全相同的比例；
  - 平均奖励、奖励标准差、KL（如果开了）、熵、输出长度、学习率；
  - 各类动作的比例，尤其是转人工的比例，用来发现「一律转人工」；
  - 格式错误率。
- **训练后**：最终模型在 A-dev 上用温度 1.0 采样，算 pass@1 和 pass@8，看 RL 是只让输出分布更集中，还是学到了新东西（Yue 等，2025）。

### 4.6 可选扩展（时间和预算够再做）

- 规模对照：用 Qwen3.5-0.8B 跑 S、SR、RR-asym。
- 思考模式和非思考模式的比较。
- 用大模型 API 加 RAG 作为参考上限（用你自己的 API key，在 Colab 上跑）。
- 多轮接待：先追问，再分流。

| 合成数据有偏差、太简单 | 用结构化事实保证答案正确；口语问法和反例单独编写；你抽检；局限性里写明 |
| 新架构的工具链不成熟 | 阶段 3 冒烟测试不通过就换 Qwen3-1.7B |
| 分流任务太简单，大模型显不出价值 | 少标注设定；放 BERT 基线；分流目标随机构变化（B 的科室不同） |
| 模型钻奖励的空子（一律转人工、乱引文档） | 奖励健全性检查；训练中盯住转人工比例和有据率；定期抽看输出 |
| Colab 断线、计算单元用完 | 检查点存 Drive、断点续训；按阶段集中使用；必要时按量加购 |
| 服务器内存不够 | 换低一档的量化，或者换 0.8B 的模型 |
| 大陆网络限制 | 模型走魔搭，pip 走国内镜像 |
| 医疗、法律方面的风险 | 只做分流、查询和转人工；演示页面写明不是医疗或法律建议；所有机构都是虚构的 |
| TRL 和 vLLM 版本不兼容 | 先用 TRL 文档推荐的版本组合，跑通后锁定版本 |
